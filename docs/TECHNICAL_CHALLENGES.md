# Technical Challenges

## 1. 기능은 늘었는데 구조는 무너지는 문제

### 문제

기존 구조는 하나의 모놀리스 패키지 아래에 controller, service, repository가 함께 자라면서 경계가 흐려졌다.  
특히 `user -> auth`, `user -> meeting`, `media -> post` 같은 직접 의존이 늘어나면서, 한 기능을 수정할 때 다른 기능의 저장소와 엔티티까지 함께 건드리게 됐다.

### 선택지

- 패키지 네이밍 규칙만 유지한다.
- 마이크로서비스로 바로 분리한다.
- 단일 배포 단위를 유지하되 모듈과 ArchUnit으로 경계를 강제한다.

### 결정

세 번째를 선택했다.  
배포 복잡도를 늘리지 않으면서도, 코드 레벨에서 의존 방향을 물리적으로 제한할 수 있기 때문이다.

### 적용

- `eventitta-app / eventitta-api / eventitta-domain / eventitta-infra`로 모듈 분리
- 도메인 간 직접 참조 대신 internal facade 도입
- `eventitta-app`에 ArchUnit 테스트를 두고 금지 의존을 지속적으로 검사

### 결과

- 기능 슬라이스를 stacked PR로 잘라 리뷰 가능한 단위로 옮길 수 있었다.
- `UserService`가 auth/meeting repository를 직접 잡던 경로를 facade로 대체했다.
- `MediaAssetService`가 post repository를 직접 참조하던 구조를 `PostInternalFacade`로 정리했다.

## 2. 모임 승인 정합성과 포인트 증감을 같은 방식으로 다룰 수 없는 문제

### 문제

모임 승인과 포인트 적립은 둘 다 동시성 문제가 있지만 성격이 다르다.

- 모임 승인: 정원 확인과 승인 처리가 결합된 check-then-act 패턴
- 포인트 증감: 현재 값을 읽지 않아도 되는 단순 산술 연산

같은 락 전략을 강제로 쓰면 한쪽은 과하고, 한쪽은 부족해진다.

### 선택지

- 전부 낙관적 락으로 처리한다.
- 전부 비관적 락으로 처리한다.
- 상황별로 전략을 분리한다.

### 결정

상황별 전략 분리를 선택했다.

### 적용

- 모임 승인에는 비관적 락을 사용해 정원 초과를 차단
- 포인트/카운터 증감에는 원자적 SQL update를 사용해 불필요한 락 대기를 줄임

### 이유

- 모임은 정합성이 핵심이므로 순차화 비용을 감수할 가치가 있다.
- 포인트 증감은 DB가 가장 잘하는 작업이므로 애플리케이션 레벨 락이 오히려 과하다.

### 결과

- 정원 초과 같은 데이터 무결성 문제를 줄이면서도
- 단순 카운터 갱신에는 불필요한 락 병목을 만들지 않는 구조를 만들었다.

## 3. 지역/거리 검색이 느려지는 문제

### 문제

거리 계산을 바로 수행하는 구조는 후보군이 많아질수록 불필요한 스캔 비용이 커진다.  
지역 기반 서비스에서 이 병목은 목록 조회 체감 성능에 직접 영향을 준다.

### 선택지

- Spatial Index로 바로 전환한다.
- 기존 스키마는 유지하면서 쿼리 구조를 최적화한다.

### 결정

기존 스키마를 유지한 채 쿼리 구조를 먼저 바꾸는 쪽을 선택했다.  
운영 리스크를 낮추면서도 충분한 개선을 얻는 것이 우선이었다.

### 적용

- Bounding Box 기반 1차 후보군 필터링
- 이후 정확한 거리 계산 적용
- 선택도를 고려한 복합 인덱스 설계
- k6 시나리오와 Grafana/InfluxDB 기반 재현 스크립트 준비

### 결과

기록해 둔 기준에서는 반경에 따라 응답 시간이 약 40~65% 개선됐다.

| 반경 | Before | After |
| --- | --- | --- |
| 3km | 29ms | 17.5ms |
| 10km | 82ms | 25.3ms |

재현 방법은 [PERFORMANCE_TEST_GUIDE.md](./PERFORMANCE_TEST_GUIDE.md)에서 확인할 수 있다.
